# Concepts

This page explains the building blocks used in the rest of the guide: the Kubernetes objects the app needs, how Kustomize and Helm are used, what the two operators do, and why every command names its cluster explicitly. If you already know Kubernetes well, skim the headings and the embedded manifests; the step-by-step pages link back here when a concept matters.

## The Kubernetes objects

Everything the app needs lives in the `dinner` namespace. Some objects come from the manifests in git, some are created by `make` from local values, and some are generated by operators at runtime.

| Object | Kind | Comes from | Purpose |
|---|---|---|---|
| `dinner` | Namespace | `k8s/base/namespace.yaml`, and `make` creates it first | Groups everything that belongs to the app |
| `app` | Deployment | `k8s/base/app.yaml` | Runs the API pod |
| `app` | Service | `k8s/base/app.yaml` | Stable in-cluster address for the pod, port 80 to 8080 |
| `app` | Ingress | `k8s/overlays/<env>/ingress.yaml` | HTTP routing rule from the ingress controller to the Service |
| `db` | CNPG `Cluster` | `k8s/base/db.yaml` | Asks the CloudNativePG operator for a PostgreSQL instance |
| `db-init` | ConfigMap | `make db-init`, from `db/init.sql` | Schema and seed data for the first boot |
| `db-app` | Secret | Generated by CloudNativePG | Database user, random password and a ready-made `uri` |
| `ocir` | Secret (docker-registry) | `make registry-secret`, OKE only | Credentials to pull the private image from OCIR |
| `dinner-tls` | Secret (TLS) | Generated by cert-manager, OKE only | The Let's Encrypt certificate and key |

### The Deployment and the Service

```yaml title="infra/k8s/base/app.yaml"
--8<-- "infra/k8s/base/app.yaml"
```

The key parts, top to bottom:

`imagePullSecrets: [ocir]`
:   On OKE the image is private, so kubelet needs credentials to pull it. The `ocir` Secret holds them. The minikube overlay removes this line because the image is already inside minikube.

`initContainers: wait-for-db`
:   Runs `pg_isready` against `db-rw` every two seconds until PostgreSQL accepts connections, and only then lets the app container start. Without it the app would start before the database is ready, and its first query would fail. The `postgres:17` image is used only because it ships the `pg_isready` binary.

`image: __OCIR_IMAGE__`
:   A placeholder, not a real image. Each environment replaces it: the minikube overlay with `dinner-roulette:local`, `make oke-deploy` with the value of `OCIR_IMAGE` (for example `eu-milan-1.ocir.io/<tenancy-namespace>/dinner-roulette:latest`). Registry and namespace differ per Oracle account, so they stay out of git.

`imagePullPolicy: Always`
:   With a moving tag such as `:latest`, kubelet checks the registry every time a pod starts, so a restarted pod gets the newest image. The minikube overlay switches this to `Never`.

`DATABASE_URL` from `secretKeyRef: db-app / uri`
:   The only configuration the app reads. CloudNativePG generates the `db-app` Secret, including a full connection string in the `uri` key. No password is ever written in git. This is 12-Factor **III. Config**: configuration lives in the environment, not in the code or the image.

`readinessProbe: tcpSocket 8080`
:   The pod is added to the Service only once something listens on port 8080. `/health` is a static handler that answers `ok` even when the database is down, so it would not add information; the TCP check at least tells when the server is up.

`resources.requests`
:   50 millicores of CPU and 128 MiB of memory. The scheduler uses these numbers to place the pod. They are small on purpose, so the app fits on the smallest node next to Postgres and the add-ons.

The Service named `app` is of type `ClusterIP`: it is reachable only inside the cluster, on port 80, and forwards to port 8080 of any pod labelled `app: app`. The outside world reaches it only through the Ingress.

### The database: a CloudNativePG Cluster

```yaml title="infra/k8s/base/db.yaml"
--8<-- "infra/k8s/base/db.yaml"
```

This is not a Deployment or a StatefulSet. It is a **custom resource**: an object type that Kubernetes does not know by default. The CloudNativePG (CNPG) operator installs the type (a CustomResourceDefinition) and a controller that watches for `Cluster` objects. When you apply this one, the controller creates:

- a short-lived pod `db-1-initdb-…` that initialises the data directory, creates the `dinner_roulette` database owned by the `dinner` role, and then runs the SQL from the `db-init` ConfigMap;
- the PostgreSQL pod `db-1` and its PersistentVolumeClaim `db-1`, which keeps the data when the pod restarts;
- three Services: `db-rw` (always the primary, the only one that accepts writes), `db-ro` (replicas only) and `db-r` (any instance);
- the Secret `db-app` with the keys `username`, `password`, `host`, `port`, `dbname`, `uri` and a few more, plus TLS certificates for the instance.

A few details worth knowing:

- `postInitApplicationSQLRefs` runs `db/init.sql` **once**, as a superuser, inside the application database, right after the cluster is created. That is why `init.sql` starts with `SET ROLE dinner;`: the tables are then owned by the app user, which can read and update them. Changing `init.sql` later has no effect on an existing database. You have to recreate the `Cluster`.
- `instances: 1` keeps the workshop small. Set it to `3` and CNPG creates two streaming replicas and fails over automatically. `db-rw` always follows the current primary, so the app does not change.
- `storage.size: 1Gi` uses the cluster's default storage class: `standard` on minikube, `oci-bv` (OCI Block Volume) on OKE, where the size is rounded up to the 50 GB minimum.

### The Ingress

An Ingress is a routing rule: "requests for host X and path Y go to Service Z". It does nothing on its own. An **ingress controller** (here ingress-nginx) watches Ingress objects and configures a real reverse proxy accordingly. `ingressClassName: nginx` selects which controller should handle the rule.

- On **minikube** the rule matches the host `dinner.local` over plain HTTP.
- On **OKE** the rule matches your domain, and the `tls` block plus the `cert-manager.io/cluster-issuer` annotation ask cert-manager for a certificate stored in the `dinner-tls` Secret.

## Kustomize: one base, two overlays

[Kustomize](https://kustomize.io/) is built into `kubectl`. It takes a set of plain YAML files (the **base**) and applies per-environment changes (the **overlays**) without templates.

```text
infra/k8s/
├── base/                 # shared by both environments
│   ├── kustomization.yaml
│   ├── namespace.yaml
│   ├── app.yaml
│   └── db.yaml
└── overlays/
    ├── minikube/         # base + HTTP ingress + local image + patch
    └── oke/              # base + TLS ingress
```


    ```yaml title="infra/k8s/overlays/minikube/patch.yaml"
    --8<-- "infra/k8s/overlays/minikube/patch.yaml"
    ```

    ```yaml title="infra/k8s/overlays/minikube/ingress.yaml"
    --8<-- "infra/k8s/overlays/minikube/ingress.yaml"
    ```

    The `images` transformer renames the placeholder `__OCIR_IMAGE__` to `dinner-roulette:local`. The JSON patch sets `imagePullPolicy: Never`, so kubelet never contacts a registry, and removes `imagePullSecrets`, since there is no `ocir` Secret on minikube.

=== "OKE overlay"

    ```yaml title="infra/k8s/overlays/oke/kustomization.yaml"
    --8<-- "infra/k8s/overlays/oke/kustomization.yaml"
    ```

    ```yaml title="infra/k8s/overlays/oke/ingress.yaml"
    --8<-- "infra/k8s/overlays/oke/ingress.yaml"
    ```

    The OKE overlay leaves the placeholder in place. `make oke-deploy` replaces it with `sed`, using the `OCIR_IMAGE` variable from `infra/.secrets.env` (or from the CI environment). That keeps the registry path of your tenancy out of git.

You can see exactly what each environment receives, without touching any cluster:

```bash
kubectl kustomize infra/k8s/overlays/minikube
kubectl kustomize infra/k8s/overlays/oke
```

## Helm: the cluster add-ons

[Helm](https://helm.sh/) installs packaged applications ("charts") into a cluster. This project uses it only for third-party components, never for the app itself. All versions are pinned at the top of `infra/Makefile`.

| Release | Chart and version | Namespace | Installed by | What it does |
|---|---|---|---|---|
| `cnpg` | `cnpg/cloudnative-pg` 0.29.1 | `cnpg-system` | `mk-deploy`, `oke-deploy` | PostgreSQL operator and its CRDs |
| `cert-manager` | `jetstack/cert-manager` v1.17.1 | `cert-manager` | `oke-up` | Requests and renews TLS certificates |
| `ingress-nginx` | `ingress-nginx/ingress-nginx` 4.12.1 | `ingress-nginx` | `oke-up` | Ingress controller, exposed through an OCI Load Balancer |

On minikube the ingress controller comes from the built-in `ingress` addon instead of Helm, and there is no cert-manager.

Every install uses `helm upgrade --install … --wait`. `upgrade --install` installs the release if it is missing and upgrades it otherwise, so re-running a target is always safe. `--wait` blocks until the release's pods are ready, so the next command never races against a half-started component.

!!! warning "ingress-nginx is retired"
    Kubernetes SIG Network [retired ingress-nginx in March 2026](https://kubernetes.io/blog/2025/11/11/ingress-nginx-retirement/). Existing charts and images keep working, but there are no more releases or security fixes. That is acceptable for a short-lived workshop cluster reachable from a single IP address. For anything long-lived, plan a move to a [Gateway API](https://gateway-api.sigs.k8s.io/) implementation or to another ingress controller.

## Operators

An **operator** is a controller that knows how to run one specific piece of software. You describe the state you want in a custom resource, and the operator does the work to get there and keep it there. Two operators are used:

- **CloudNativePG** turns a `Cluster` resource into PostgreSQL pods, volumes, Services and Secrets, and handles failover, backups and upgrades.
- **cert-manager** turns a `ClusterIssuer` plus an annotated Ingress into a valid certificate, and renews it before it expires.

Both are installed cluster-wide with their CRDs. That is why `make` installs them before applying the app manifests: applying a `Cluster` before the CRD exists fails with `no matches for kind "Cluster"`.

## kubeconfig, contexts and `--context`

`kubectl` reads its connection settings from a **kubeconfig** file. A kubeconfig lists clusters (API address and CA), users (credentials) and **contexts** (a cluster plus a user). The "current context" is the one used when you do not say otherwise.

This project is careful never to depend on the current context:

- `minikube start` writes a context called `minikube` into `~/.kube/config`.
- `make oke-up` writes the OKE credentials into a separate file, `infra/kubeconfig` (git-ignored), and renames that context to `oke`. Your `~/.kube/config` is never modified.
- The `Makefile` exports `KUBECONFIG=$HOME/.kube/config:<repo>/infra/kubeconfig`. A colon-separated list makes `kubectl` merge both files into one view.
- Every `kubectl` and `helm` command in the `Makefile` passes `--context minikube`, `--context oke` or `--kube-context …` explicitly.

The result is that a production context that happens to be selected in your shell can never receive these manifests by accident. When you want to use plain `kubectl` yourself, `make mk-env` and `make oke-env` print the two lines that set `KUBECONFIG` and switch context:

```bash
eval "$(make mk-env)"    # or: eval "$(make oke-env)"
kubectl get pods -n dinner
```

## The idempotent "create, then apply" pattern

You will see this pattern several times in the `Makefile`:

```bash
kubectl create namespace dinner --dry-run=client -o yaml | kubectl apply -f -
```

`kubectl create` fails if the object already exists, while `kubectl apply` creates or updates. The `--dry-run=client -o yaml` flags make `create` print the object as YAML instead of sending it, and `apply` then sends it. The same trick builds Secrets and ConfigMaps from literal values or files. Every target can therefore be run again and again without errors, which matters when a long `make oke-up` stops halfway and you simply run it a second time.

## Where the 12 factors show up

The workshop is about the [12-Factor App](https://12factor.net/). This is where the deployment puts some of the factors into practice:

| Factor | In this setup |
|---|---|
| III. Config | `DATABASE_URL` comes from the environment, filled from a Secret. The image never contains environment-specific values. |
| IV. Backing services | Postgres is attached through a URL. Replacing CNPG with a managed database only means changing the Secret. |
| V. Build, release, run | The image is built once (CI or `make oke-push`). The release is that image plus the manifests and Secrets. Pods are the run stage. |
| VI. Processes | Votes are in Postgres, not in the process. Deleting the app pod loses nothing, as the [minikube walkthrough](minikube.md#step-5-prove-that-the-pod-is-disposable) shows. |
| IX. Disposability | The init container and the readiness probe make start-up predictable. Graceful shutdown is still a workshop exercise. |
| X. Dev/prod parity | The same base manifests and the same Postgres operator run on minikube and on OKE. |
| XI. Logs | Still broken on purpose: the app writes to `logs/app.log` inside the container, so `kubectl logs` shows almost nothing. See [Day-2 operations](oke/operate.md#read-the-logs). |
